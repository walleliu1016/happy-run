# 律动跑酷 · UI 版式规范 v1（TV 优先）

| 项 | 值 |
|---|---|
| 文档版本 | `ui-layout-spec@v1` · 2026-11-26 |
| 适用项目 | WarmingUp 律动跑酷（Vite + TypeScript + Three.js r160 + DOM UI） |
| 目标载体 | Android TV / 电视盒子 WebView（`?tv=1`）→ 手机浏览器（强横排）→ 720p 低配盒子 |
| 主设计基准 | **1920 × 1080 @1x** |
| 交付阶段 | **A 版式定规**（本文档）→ B/C/D 逐屏资源 → E 落地清单 |
| 状态 | 版式数字已确认；配色方向已由用户拍板 **B 熔岩运动** 并于 P16 落地（见 `律动跑酷-B版落地清单.md`） |

---

## 0. 结论先行

1. **本次「全新 UI」= 版式规格体系重构 + TV 优先适配，不推翻 v1 玩法与交互资产。** 版式数字全部受保护；配色已由用户拍板换为 B 熔岩运动（P16 已落地），Joy 图标 / 分组列表 / 金圈焦点 / 强横排保持不变。
2. **根因是规格缺失，不是美术问题。** 现状字号 144 个不同取值、`:root` 无 spacing/type/z-index token、TV 断点 `min-width:2200px` 在 1920 上永不命中、靠 `zoom:1.18` 与横排旋转相乘 → 同一元素在不同设备上忽大忽小，横幅「看起来一边宽」正是这个漂移的症状。
3. **建立单一缩放基准 `--s`，弃 `zoom`。** 所有尺寸以 1920×1080 设计单位 `u` 表达，乘 `--s` 落地；TV 与手机**字号用离散档表**，不按 `--s` 等比缩（观看距离不同，等比缩会把 TV 正文压成 12px）。
4. **TV 最小可读字号 24px @1080p，硬下限 20px @720p。** 现状 9–13px 的小字在 3m 观看距离下不可读，必须按 §5 档表收敛。
5. **DOM/CSS 项目里「可切图资源」需要重新定义。** 底板/按钮/卡片/描边一律**纯 CSS**，切九宫格位图在 DOM 里会糊、装不下多语言、还撑大包体；真正要出位图的只有「发光/粒子贴图」与「复杂纹理插画」，图标统一 SVG 矢量家族。详见 §9。
6. **老电视内核能力基线必须写进规范。** `:has()`、`cqw`、`aspect-ratio`、`inset` 在 Chrome 60–79 上静默失效，规范给出替代写法（§10）。这是「TV 显示不完美」的第二个技术根因。

## 1. 设计基准与缩放策略（已确认 / 本次假设）

**结论：主基准 1920×1080 @1x；用单一缩放因子 `--s` 取代现状的 `zoom` + 旋转 + `dvh` 三重叠加。**

| 项 | 值 | 依据 |
|---|---|---|
| 主设计基准 | `1920 × 1080` @1x | 项目全部 TV 截图脚本 `shots*.mjs` 的实测视口；Android TV 1080p 标准 |
| 设计单位 | `1u = 1px @1920 基准` | 便于跨分辨率整体乘算，不为每个宽度重写 clamp |
| 缩放因子 | `--s = min(vw / 1920, vh / 1080)` | 短边优先，极宽/极窄屏不拉伸、只留白 |
| 极宽屏（≥2200） | `--s` 按**高度**算，内容栏 1440u 居中 | 现状 `min-width:2200px` 断点放大 padding 会导致内容横跨过远 |
| 像素栅格 | 所有尺寸/位置对齐 **4u**；绑定值允许 2u | 避免半像素模糊与缝隙；栅格列宽属推导值，不强制 4u |
| 垂直基线 | **8u** 行网格 | 行高、间距、图标尺寸共用 8 的倍数 |

**为什么弃 `zoom`**：现状 `.tv-mode` 用 `zoom:1.18` + `height:calc(100vh/1.18)`，同时 `body.force-landscape` 对整个 `#app` 做 `rotate(90deg)`，`#app` 又是 `100dvh`。旋转 × 缩放 × 高度重算相乘后，任何静态盒模型推导都失效（P13 探针实测 `getBoundingClientRect` 返回旋转后的条带坐标，横幅厚度与 CSS 声明对不上）。`transform: scale()` 或 CSS 变量乘算在老 Chromium 上行为确定，且不影响 `getBoundingClientRect` 的语义一致性。

**落地配置写法（CSS 层，非运行时逻辑）**：

```css
:root {
  --s: 1;                 /* 由 .tv-mode / 视口档位给定，不写 JS */
  --u: calc(1px * var(--s));
  --col: calc(122 * var(--u));
  --gutter: calc(24 * var(--u));
  --margin: calc(96 * var(--u));
}
```

> 现状 `clamp()` 在 Chrome <79 不支持，降级路径用**离散档固定 px**（见 §10），不依赖 `clamp()` 求值。

### 1.1 目标分辨率矩阵（本次假设，可一行改）

|---|---|---|---|---|---|

## 2. 安全区

**结论：TV 按 5% overscan 内缩，内容区 1728×968u；关键文案/按钮再进 2.5% 到标题安全区 1632×912u。**

| 具名值 | @1920 基准 | @720p | 说明 |
|---|---|---|---|
| `--safe-h`（左右） | **96u** | 64u | 1920×5% = 96，正好对齐 4u 栅格 |
| `--safe-v`（上下） | **56u** | 40u | 1080×5% = 54，取整到 4u → 56 |
| `--title-h` | **144u** | 96u | 关键文案/比分/主按钮的左边界 |
| `--title-v` | **84u** | 56u | 关键文案上下边界 |
| 内容安全区尺寸 | `1728 × 968` | `1152 × 640` | = 视口 − 2×safe |
| 标题安全区尺寸 | `1632 × 912` | `1088 × 608` | = 视口 − 2×title |
| 底部提示条避让 | **56u** | 40u | `#tv-hint-bar` 占高，内容区底部额外让出 |

**移动端**：四个方向取 `max(上表值, env(safe-area-inset-*))`。强横排 `rotate(90deg)` 后 inset 方向交换（`top↔right`、`bottom↔left`），必须按旋转后的实际屏幕方向映射，不能直接用 `env()` 原值 —— 这是现状弹层贴边算法的已知坑。

**拦截规则**：任何可交互元素（含焦点目标）不得越出内容安全区；Toast 可贴近边缘但不进入 overscan 区（会被电视裁掉）。

## 3. 栅格系统

**结论：12 列 / gutter 24u / margin 96u（= 安全区水平边距）/ 列宽 122u；信息型屏内容栏 1440u 居中，沉浸型屏用满 1728u。**

```
|<-- 96u margin -->|  1728u 内容安全区  |<-- 96u -->|
| [col 122] 24 [col] 24 ... ×12 ... [col 122] |
12×122 + 11×24 = 1464 + 264 = 1728 ✓
```

| 项 | 值 | 依据 |
|---|---|---|
| 列数 | **12** | 可被 2/3/4/6 整除，覆盖海报墙、分屏 PK、分组列表、统计卡 |
| 列宽 | 122u（推导值） | (1728 − 11×24) / 12 |
| gutter | 24u | 3×8u 垂直基线；TV 上相邻焦点块的最小间隔 |
| margin | 96u | 直接复用 overscan，避免「安全区外还有栅格」 |
| 信息型屏内容栏 | **1440u 居中** | 现状 `.set-wrap`/`.pf-hero`/`.result-card` 锁 860px，在 1920 上只占 45%，3m 距离下视线横跨过大且文字显小；1440 = 12 列栅格内 10 列 + 9 gutter（1220+216=1436≈1440） |
| 沉浸型屏 | 满 1728u | 游戏 HUD、过场、PK 分屏、结算舞台 |
| 竖屏/窄屏 | 12 → 6 → 4 列 | ≤720u 走 6 列，≤430u 走 4 列；**不用 `repeat(2,1fr)` 覆盖海报网格**（已确认红线） |

**栅格用法举例**：菜单页 = 左 8 列（关卡海报墙）+ 右 4 列（横幅/挑战/PK 入口）；准备页 = 内容栏 1440u 内 12 列；PK 分屏 = 左右各 6 列，中间 gutter 24u 作分屏缝。

> **P13 关联结论**：`.room-banner` 与 `.daily-banner` 的 CSS 盒模型实测完全一致（同 `padding: clamp(12px,1.4vw,20px) clamp(16px,1.8vw,28px)`、同 gap、同 radius），用户截图里「紫条更宽」是 TV 环境下 `zoom`×旋转×断点错位造成的排布漂移，不是两条写了不同尺寸。新版把 `.room-banner` / `.daily-banner` / `.ghost-banner` **统一为同一 `.banner` 规格**（现状 ghost 用了另一套 `14/18px` padding + 固定 `16px` gap），并纳入 12 列栅格的固定列跨度，从根上消除同类元素尺寸漂移。

## 4. 层级（五层）与遮罩 / 拦截

**结论：五层固定 z-index token 取代现状硬编码 `5/6/12/60/70/80/90/100`。**

| 层 | 内容 | z-index token | 遮罩 | 输入拦截 | 焦点 |
|---|---|---|---|---|---|
| **L0 背景** | 页面底、Three.js 画布、氛围光、速度线 | `--z-bg: 0` | — | 不拦截 | 不可聚焦 |
| **L1 内容** | 屏内卡片、列表、分组行、HUD 常驻信息 | `--z-content: 10` （范围 10–29） | — | 正常 | 主内容区 |
| **L2 浮层** | Toast、TV 提示条、姿态提示、下拉、排行榜 | `--z-float: 30`（30–49） | 无 / 局部半透 | Toast 不拦；下拉拦截其下 | 通常不进焦点链 |
| **L3 弹窗** | nick / calib / pad / invite modal | `--z-modal: 50`（50–69） | `rgba(10,10,20,.55)` + `blur(8px)`（沿用已确认值） | **全屏拦截** | **困焦点**（最上层 `.show` 弹层内循环） |
| **L4 引导 / 过场** | `level-intro`、`screen-wipe`、confetti | `--z-wipe: 80`（80–99） | 不透明 | 全屏拦截，禁输入 | 不进焦点链 |

**规则**：
- 同一时刻**只有一个 L3 弹窗**处于 `.show`；新弹窗打开时旧弹窗必须退场，避免两个困焦点层叠加。
- L2 的 Toast **不得**抢焦点，且不得覆盖主按钮的点击区（现状 `z-index:100` 高于 wipe，需收敛到 `--z-float`）。
- `[hidden]` 统一用 `display:none!important` 兜底（现状已如此，保留），但**新组件不得依赖它做状态切换**，用显式 `.is-hidden` 类 + 状态矩阵。
- 五层之外不再新增层级；需要「浮在弹窗之上」的元素归入 L3 内部子层（10–19 局部）。

## 5. 字号阶梯（五档 + HUD 特例）

**结论：TV 1080p 最小可读 24u；五档收敛现状 144 个取值；TV 与手机用离散档表，不按 `--s` 等比缩。**

### 5.1 TV-1080（主基准，@1920）

| 档 | 用途 | 字号 | 行高 | 字重 | 字距 |
|---|---|---|---|---|---|
| **T1 标题** | 屏标题、过场主标、结算评级 | **56u** | 1.15 | 800 | −0.02em |
| **T2 副标题** | 分组标题、卡片标题、弹窗标题 | **36u** | 1.25 | 700 | −0.01em |
| **B1 正文** | 按钮、列表主文案、说明正文 | **28u** | 1.40 | 600 | 0 |
| **B2 辅助** | 副文案、单位、时间戳、角标 | **24u** | 1.40 | 500 | 0 |
| **N 数值** | 比分、星数、计时、连击 | **40u** | 1.10 | 800 | `font-variant-numeric: tabular-nums` |
| **D1 显示级（仅游戏 HUD）** | 倒计时、COMBO、大字判定 | 96u | 1.00 | 900 | −0.03em |

**为什么是 24u 下限**：Android TV 在 1080p / 2.5–3.5m 观看距离下的正文下限约 24sp；现状 `9px`/`11px`/`11.5px`/`12px` 的小字在电视上不可读。B2 24u 是硬下限，**任何 TV 可见文字不得小于 24u**。D1 是游戏 HUD 特例（瞬间扫读、停留 <1s），不进入常规屏。

### 5.2 离散档表（跨设备，不用等比缩放）

| 档 | TV-1080 | TV-720（下限 20u） | Phone-L 844×390 | Phone-P 390×844 |
|---|---|---|---|---|
| T1 | 56 | 38 | 28 | 26 |
| T2 | 36 | 24 | 20 | 18 |
| B1 | 28 | 20 | 16 | 15 |
| B2 | 24 | **20**（不取 16） | 14 | 13 |
| N | 40 | 28 | 22 | 20 |
| D1 | 96 | 64 | 56 | 48 |

**依据**：手机是 30–40cm 手臂距离，TV 是 2.5–3.5m，纯 `--s` 等比会把 TV 正文 28u 压成手机 12u 再放大回 TV 时失真；离散档是「连续值 vs 离散值适配」的标准处理。TV-720 的 B2 强制抬到 20u 而非 16u，就是为低配盒子留可读性余量。

### 5.3 文本布局余量

- 所有文本容器按**最长语种留 30%–50% 余量**，不做刚好卡满（中 ↔ 英/德/俄）。
- 单行标题用 `text-overflow: ellipsis; white-space: nowrap`，但**关键文案不得被省略** —— 关键文案容器按 50% 余量给宽度。
- 字体栈沿用已确认的 `--font`（SF Pro / PingFang SC / HarmonyOS Sans / system-ui）；TV 上优先命中系统中文黑体，字重只用 `500/600/700/800/900` 五档，禁用 400 以下。
- **图内不放文字**（已确认红线）：所有文案 DOM 渲染，位图资源不含任何字符。

## 6. 点击区与 TV 焦点

**结论：触屏 ≥88×88 逻辑 px；TV 焦点目标 ≥120×64u；视觉尺寸与命中区分离；消除现有「蓝 outline + 金圈」双轨高亮。**

| 项 | 值 | 依据 |
|---|---|---|
| 触屏最小命中区 | **88 × 88 逻辑 px** | 体感游戏运动中操作，比 iOS 静态 44pt 下限留一倍余量 |
| TV 焦点目标最小 | **120 × 64u** | 金圈外扩 12u + 3m 距离可辨识；现状 44/52px 在 1920 上过小 |
| 相邻焦点目标间距 | **≥24u** | 与 gutter 一致；低于此值十字就近算法（`cross×2.2`）易误跳 |
| 视觉尺寸 vs 命中区 | 分离 | 小图标按钮用透明 `::before` 扩命中区，视觉尺寸不变 |
| 焦点环（TV） | 沿用**已确认 `.tv-focus` 金圈**，`@1920` 调为：白内环 **4u** / 金外环 **12u** / 光晕 **48u** / `scale(1.04)` | 现状 3/9/32px 是手机尺度，TV 上太细 |
| 焦点色 | `--focus-gold: #ffb020`（变量化现状 `rgba(255,176,32,*)`） | 与 8+ 种橙/金硬编码并存的乱象收敛 |
| 双轨消除 | `.tv-focus` 生效时 `:focus-visible` 的 `outline` 必须为 `none` | 现状 `el.focus()` 同时命中两套高亮（蓝框 + 金圈叠加） |
| 焦点落位 | 进屏/弹层自动落主内容区（非 topbar）、从哪来回哪去、弹层困焦点 | 已确认的 TV 焦点体系，不改逻辑，只统一尺寸 |

`--focus-gold` 是**唯一**焦点色；`:focus-visible` 的 `var(--blue)` 保留给纯键盘/外接设备，不用于 TV 遥控路径。

## 7. 状态矩阵（五态，缺态即返工）

**结论：每个可交互元素必须定义 常态 / 按下 / 禁用 / 选中 / 焦点 五态。**

| 态 | 底色 | 描边 | 形变 | 阴影 / 光晕 | 可聚焦 |
|---|---|---|---|---|---|
| **常态 `n`** | 组件基色 | 1u 半透明白 | — | 常规投影 `0 18u 42u rgba(0,0,0,.35)` | ✅ |
| **按下 `p`** | 亮度 −8% | 不变 | `scale(.97)` | 投影移除 | ✅ |
| **禁用 `d`** | `opacity:.4` | 不变 | — | 全部移除 | ❌（`FOCUSABLE` 已排 `[disabled]`，加 `aria-disabled`） |
| **选中 `s`** | 主色 8% 叠加 | 2u 主色实线 | — | 常规 | ✅ |
| **焦点 `f`（TV 专属）** | 不变 | 见 §6 金圈 | `scale(1.04)` | 金光晕 48u | ✅ 唯一 |

**逐控件落点**：

| 控件 | 常态 | 选中态特征 | 焦点态特征 |
|---|---|---|---|
| `.btn` / `.btn-primary` | 药丸 `radius:999u`；`min-height:88u`（TV） | 主色底 + 白字 | 金圈光晕 48u（primary 用 64u） |
| `.mode-card` | `radius:24u`；`border:2u transparent` | 主色 2u 描边 + 左侧 4u 竖条 | 金圈 + `z-index` 提一级 |
| `.level-poster` | `radius:24u`；`aspect-ratio` 替代写法见 §10 | 主色 3u 描边 | 金圈（不裁切，溢出到 gutter） |
| `.banner`（room/daily/ghost 统一） | `radius:24u`；`padding:20u 28u`；`gap:20u` | 不设选中 | 金圈 + 尾部箭头位移 4u |
| `.set-row` | 分组内 1u 分隔线；`padding:16u 20u` | 右侧对勾（已确认样式） | 整行金圈，不逐格聚焦 |
| 输入 / `.pk-code-input` | 1u 描边；`min-height:88u` | — | 金圈 + caret 可见 |
| 图标按钮 | 视觉 48u / 命中 88u | 主色填充 | 金圈 |

**注意**：`prefers-reduced-motion: reduce` 时关闭所有 `sheen-loop` / 呼吸动画（现状已有两条 `@media`，收敛为一条全局规则）。

## 8. 圆角 / 描边 / 阴影 token

**结论：收敛现状 10+ 种圆角、8+ 种金色、4 套热区为固定 token 表。**

| token | 值 | 取代现状 |
|---|---|---|
| `--r-sm` | 8u | 6/10/12px 零散值 |
| `--r-md` | 16u | 14/16/18px |
| `--r-lg` | 24u | `--radius:22px`、20px 海报/头卡 |
| `--r-pill` | 999u | 药丸按钮/Toast/TV 提示条 |
| `--border-hair` | 1u `rgba(255,255,255,.12)`（暗底）/ `rgba(0,0,0,.07)`（浅壳） | 两套硬编码 |
| `--border-strong` | 2u 主色 | `.mode-card` 2px transparent |
| `--shadow-card` | `0 18u 42u rgba(0,0,0,.35)` | 现状 `--shadow` 浅壳 `0 12px 40px rgba(0,0,0,.08)` 与暗底各写一套 |
| `--glow-gold` | `0 0 48u rgba(255,176,32,.55)` | 现状 32px/40px 两档 |
| `--space-1..6` | 8 / 16 / 24 / 32 / 48 / 64 u | 现状 4/5/6/7/8/9/10/12/14/16/18/20/22/26/28/30/36/48px 全散落 |

**色板双轨（已确认，保护）**：信息型屏为浅色外壳（`--bg:#f5f5f7` / `--ink:#1d1d1f` / `--blue:#0071e3`），游戏屏与海报/横幅为霓虹暗色（`#070312` 底 + `#ffd60a` 金 / `#ff375f` 粉 / `#7df0ff` 青 / `#7b2ff7` 紫）。规范**不换这两个锚点**，只把 110 个硬编码 hex 收敛到下列 12 个语义 token：

`--c-bg / --c-surface / --c-ink / --c-ink-2 / --c-brand / --c-success / --c-warn / --c-danger / --c-neon-gold / --c-neon-pink / --c-neon-cyan / --c-neon-purple`，暗底/浅壳通过 `[data-theme="stage"]` 覆盖同一组语义名，不再按组件各写一个 hex。

## 9. 切图与九宫格判定（DOM 落地映射）★

**结论：这是网页 DOM/CSS 项目，不是 Unity/Unreal 项目 —— 大部分「底板」根本不该切图。用户要的「可切图资源」按本节重新划界。**

| 元素 | 现状 | 规范做法 | 是否出位图 |
|---|---|---|---|
| 纯色 / 渐变底板、药丸按钮、卡片 | `linear-gradient` + `border-radius` | **纯 CSS**（`--r-*` + 渐变 + `--shadow-card`） | ❌ 不切 |
| 圆角描边 / 渐变边框 | `border` / 双层 background | `border` + `background-clip:padding-box` | ❌ 不切 |
| 分组列表行、分隔线 | CSS | 纯 CSS | ❌ 不切 |
| **图标（Joy 等）** | 1 个 `#icon-joy` symbol + 大量 emoji | **统一 SVG 矢量家族**（`<symbol>` + `<use>`），不出位图 | ❌ 位图；✅ SVG symbol |
| **发光 / 粒子 / 速度线 / 打击光效** | CSS 光晕 / canvas 运行时生成 | **位图 PNG-24 带 alpha**，叠加模式 `screen`；发光留白 ≥20% | ✅ 切 |
| **复杂纹理 / 关卡海报插画** | CSS 渐变 + `cqw` 文字 | **位图，无文字**（文字一律 DOM 叠层） | ✅ 切 |
| 文字 / 数值 / 按钮文案 | 图内文本（风险） | DOM 渲染 | ❌ 绝不入图 |

**为什么不切底板九宫格**：DOM 里用 9 片 PNG 拼一个按钮，在 720p↔4K 之间必然糊、多语言文本放不进图、包体变大、还要为每个宽度出图；纯 CSS 一套代码全分辨率清晰。**九宫格只在「将来移植到游戏引擎」时才启用**，因此本规范仍给出跨引擎可复用的四个具名边界值：

### 9.1 九宫格边界（引擎中立规格，供未来移植）

示例底板：`radius:24u`、描边 `2u`、内容区最小 `1u`

| 具名值 | 值 | 说明 |
|---|---|---|
| `border.left` | **28u** | 24 圆角 + 2 描边 + 2 保护 |
| `border.top` | **28u** | 同上 |
| `border.right` | **28u** | 同上 |
| `border.bottom` | **28u** | 同上 |
| 可变区 | ≥1u | 中间 1u 拉伸，四角与描边不参与 |
| 切图尺寸 | `56 × 56u`（最小）→ 出 `112 × 112u` @2x | 2 的幂友好，够 4K |

> **参数顺序红线（四引擎不同，写序列必然接反）**：Unity = 左·下·右·上；Unreal / Godot = 左·上·右·下；Cocos = 左·右·上·下。本规范只写四个**具名值**，落地时按目标引擎排列。
> **Cocos 特别注意**：Border 绑在 SpriteFrame 资源上，一个 SpriteFrame 只能有一套九宫格参数；同一底板要两种边界必须出两张图。
> 本项目（DOM/WebView）当前**不需要**这套参数；它随规格一起存档，保证同一套设计将来能平移进引擎而不重做。

### 9.2 位图资源规范

| 项 | 值 |
|---|---|
| 格式 | PNG-24 + alpha（发光/贴图）、SVG（图标） |
| 倍率 | `@1x` @1920 基准；`@2x` 供 4K |
| 透明边 | 四边 ≥8u 全透明；发光贴图发光留白 ≥20%，防过曝裁切 |
| 叠加模式 | 发光 `screen` / 粒子 `add`；禁止 `normal` 直接压暗底 |
| 序列帧 | 等分切分、逐帧对齐中心点（本项目暂不产，属兄弟专家归口） |
| 图内文字 | **禁止** |

### 9.3 命名与图集分组

```
ui_<屏>_<组件>_<状态>@<倍率>@<版本>.png
例：ui_menu_banner_n@1x@v1.png / ui_fx_hit_glow@2x@v1.png
状态后缀：_n 常态 / _p 按下 / _d 禁用 / _s 选中 / _f 焦点
图标：icon_<名称>.svg（symbol id 与文件同名）
```

| 图集组 | 内容 | 尺寸预算 |
|---|---|---|
| `ui_common` | 跨屏底板、按钮、分隔线（CSS 为主，位图仅纹理） | ≤1024² |
| `ui_menu` | 海报插画、横幅纹理 | ≤2048² |
| `ui_game` | HUD 贴图、速度线、判定环 | ≤2048² |
| `ui_fx` | 发光、粒子、打击光效 | ≤1024² |
| `ui_result` | 评级、段位徽章、彩带 | ≤1024² |

Web 无图集硬上限，分组按「按屏 + 使用频率」以便合并请求；单张 ≤2048² 以便将来 2 的幂纹理友好。**所有 AI 生成图需人工精修与合规确认后才能作为最终素材**，本规范不承诺「生成即可商用」。

### 10.2 老电视 WebView 能力基线（Chrome 60–79，已确认红线）

**结论：现状使用了 4 个在老内核上静默失效的 CSS 特性 —— 这是「TV 显示不完美」的第二个技术根因。**

| 特性 | 最低 Chrome | 现状 | 规范替代写法 |
